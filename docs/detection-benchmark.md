# 题型检测基准：量表 vs 计数变量

> 2026-07-31。对应实现：`src/question_type_detector.py`。
> 测试：`tests/test_detection_scale_vs_count.py`，
> fixture：`tests/fixtures/detection/scale_vs_count.json`。

## 1. 背景：一个修复请求

外部效度检验（见 `docs/external-validity-check.md`）发现，
`_is_scale_question` **识别不了任何以 0 开头的量表**——NPS、0-10 信任电池、
0-10 生活满意度阶梯全部落到 `numeric question`，永远进不了量表处理路径。

看起来是两处闸门的问题：

1. `in_scale_range` 要求 `1 <= min_value`；
2. 放宽下界后，0-10 的 **11 个不同取值**又被 `unique_count > 10` 卡掉。

**但"能识别 0-10 了"只是正方向。** 反方向是：放宽之后，**什么会被误判成量表**。

## 2. 反方向的真实风险：计数变量

计数变量（count variable）与李克特量表在**取值上完全同形**：

| 列 | 取值 | 语义 |
| --- | --- | --- |
| 「家里有几个孩子」 | 0,1,2,3,4 | 计数 |
| 某 5 点李克特题（0 起编码） | 0,1,2,3,4 | 量表 |

**两者的数值分布无法区分。** 一旦计数变量被判为量表，它会走量表处理路径：
按李克特口径算均值、可能被纳入构念得分（composite score）、
在报告里以"量表题"呈现。这是实打实的回归。

## 3. 测量

语料 21 列（10 个量表、10 个计数、3 个歧义），每列 300 行，
确定性生成（见 fixture 的 `seed`）。

| 状态 | 量表召回率 | 计数变量误判率 |
| --- | ---: | ---: |
| **S0 现状** | 6/10（60%） | 2/10（20%） |
| **S1 只放宽下界** | 8/10（80%） | 7/10（**70%**） |
| **S2 下界 + unique 上限** | 10/10（**100%**） | 10/10（**100%**） |
| **S3 S2 + 列名关键词** | 10/10（100%） | 3/10（30%） |
| **S4 S3 + 「数」后缀规则** | 11/11（100%） | 0/10（**0%**） |

### 三条必须读出来的结论

1. **S1 是半修复，且代价惊人。** 0-4 与 0-6 恢复了，**0-10 仍然失效**，
   而计数误判率已经从 20% 涨到 70%。只做下界修改的人会以为修好了——
   在 5 点量表上一切正常。
2. **S2 完全丧失区分力。** 召回 100%，误判也 100%：
   **每一个计数变量都变成了量表。** 单靠放宽阈值不可能同时满足两端。
3. **只有引入列名信号才能同时压住两边。** 这不是调参能解决的，
   是必须引入取值之外的新信息。

### S0 现状里已经存在的误判

不是修复引入的：任何取值范围恰好落在 1-5 / 1-7 / 1-10 窗口内的计数变量，
**今天就已经被判成量表**——语料中的「家庭人口数」(1-8) 与「房间数量」(1-6) 即是。

## 4. 列名倾向判断（(c) 的尝试与结论）

**做法**：新增 `COUNT_NAME_KEYWORDS = (次数, 个数, 数量, 人数, 天数, 频次,
count, number, times, num_, _num, qty)`，命中即判定为非量表；
再补一条「列名以『数』结尾」的后缀规则，并排除 `分数 / 度数`。

**效果**：见上表 S3 → S4，误判率 30% → 0%，召回率不受影响（11/11）。

**结论：可以做，但必须限定它的可信度。** 三条保留意见：

1. **语料与启发式同源。** 21 个列名与这套关键词都是我写的，
   这与 `golden_survey.json` 是同一种循环。真实平台导出的列名
   （`Q12`、`item_3`、`A1_1`）不在其中。
2. **「排除 `分数/度数`」这类特例是过拟合的信号。** 每加一个例外，
   就说明规则在贴着我的样本走。
3. **中文后缀规则不可移植到英文。** `visit_count` 靠关键词命中，
   `n_kids` 则不会——英文侧仍需扩表。

因此这套启发式的定位是**降低误报，而非解决问题**。真正的解在第 5 节。

## 5. 不可约的歧义（irreducible ambiguity）★

> **这一节是"全流程（survey end-to-end）"设计论点的核心证据。**

考虑两列：

```
列名: Q12        取值: 0,1,2,3,4    →  可能是 5 点量表，也可能是「孩子数」
列名: item_3     取值: 0,1,2,...,10 →  可能是 NPS，也可能是「本月购买次数」
```

**0-10 的 NPS 与 0-10 的购买次数，在取值上完全无法区分。**
它们的取值集合相同、分布可以相同、缺失模式可以相同。列名一旦是
`Q12` / `item_3` / `A1_1` 这类平台生成的编号（这在真实回收数据里是常态），
连第 4 节的列名信号也一并失效。

**这不是检测器写得不够好，是信息本身不足。** 纯检测（inference from data
alone）在这里没有解——任何阈值、任何词表、任何模型都无法从相同的数字里
读出不同的语义。

**只有 schema 能消歧。** 如果这份数据来自本工具生成的问卷，
schema 里写着 `question_type=scale, points=11, min_value=0`，
歧义在生成时就已经被消除，回收时只需对齐（见
`docs/specs/survey-generation-module.md` §12）。

这正是把工具定位为**问卷全流程**而不是**通用数据分析**的实质理由：

- **通用数据分析**只能拿到回收数据，注定要在这个歧义上猜；
- **问卷全流程**在生成端就持有语义，回收端只需匹配，**从根上不需要猜**。

fixture 的 `ambiguous` 组（`Q12` / `item_3` / `v7`）把这三列固化下来，
测试断言的不是"检测器判对了"，而是"**这三列的判定本质上是掷硬币**"。

## 6. 当前状态与后续

- 本文档记录的是**修复前**的基线。`tests/test_detection_scale_vs_count.py`
  已把 S0 的逐列判定与两个比率（6/10、2/10）固化。
- 修复（S4 方案）属于批 1.5 范围，届时须**同步更新** fixture 的 `expected`、
  测试里的比率断言、以及本文档第 3 节的表格，并在提交信息中说明改动。
- 语料规模（21 列）偏小，且与启发式同源。扩充语料、特别是加入真实平台
  导出的列名，是提高本基准可信度的下一步。
