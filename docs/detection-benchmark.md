# 题型检测基准：计数变量正在被当成量表

> 2026-07-31。对应实现：`src/question_type_detector.py`。
> 测试：`tests/test_detection_scale_vs_count.py`，
> fixture：`tests/fixtures/detection/scale_vs_count.json`。

## 1. 主要发现与修复：计数变量曾被判为量表

`_is_scale_question` 曾把**任何取值范围恰好落在 1-5 / 1-7 / 1-10 窗口内的
计数变量判定为量表题**。这不是任何改动引入的，是既有行为：

| 列（真实语义） | 取值 | 修复前 | 修复后 | 降级理由 |
| --- | --- | --- | --- | --- |
| 家庭人口数 | 1-8 | ❌ scale | ✅ numeric | `count_name:人口` |
| 房间数量 | 1-6 | ❌ scale | ✅ numeric | `count_name:数量` |

误判率 **2/10（20%）→ 0/10（0%）**，**真量表召回率 6/10 保持不变**。

### 1.1 为什么这件事严重

题型不是只影响一个标签，它决定下游怎么解释这列数字。
一个被判成量表的计数变量会：

1. 走量表描述统计（`summarize_scale_questions`），按李克特口径算均值与分布；
2. 可能被纳入构念得分；
3. **进入报告与 AI 解读层**——`ai_report` 拿到的是"量表题均值 3.2"，
   于是把"平均购买 3.2 次"叙述成"平均评分 3.2 分"。

**这是自信地说错话，而且是用户最难察觉的一类错误。** 报告读起来完全正常，
数字也对，只有语义是错的。

### 1.2 修复方式：把词表用在降级方向上

列名命中计数关键词（`次数 / 个数 / 数量 / 人数 / 人口 / 天数 / 频次 / 件数 /
笔数 / count / number / times / frequency / qty / num_`）**且未命中量表关键词**时，
把已判为 scale 的列**降回 numeric**，并记录降级理由供用户复核与撤销
（走既有的 `POST /api/{sid}/types` 覆盖）。

**为什么这次可以用这套词表，而 §4.1 说它过拟合**——因为方向反了，错误代价也反了：

| 方向 | 判错的后果 | 可接受？ |
| --- | --- | --- |
| 用词表**提升**为量表 | 计数变量变量表 → 报告把"3.2 次"讲成"3.2 分" | ❌ 危险 |
| 用词表**降级**为数值 | 真量表变数值题 → 信息变少，均值仍合法 | ✅ 安全 |

这是一个**单调安全（monotone-safe）**的改动：最坏情况只能把东西推向安全一侧，
**不可能制造新的危险误判**。词表的过拟合问题因此在这个方向上不成立。

量表关键词优先级更高，`满意度分数` / `满意度频次` / `agreement_frequency` /
`评分次数` 均不被降级。

**已知代价（如实记录）**：列名含 `frequency` 且无评分词的英文李克特题会被降级，
实测 `frequency_of_use`(1-5) → numeric。中文 `使用频率` 不受影响（词表收的是
`频次` 而非 `频率`）。代价是信息变少加一次手动覆盖，属安全一侧。

## 2. 一个次要缺口：0 起量表识别不了

同一个函数的 `in_scale_range` 要求 `1 <= min_value`，所以**任何以 0 开头的量表
都落到 `numeric question`**——NPS（0-10）、0-10 信任电池、0-10 满意度阶梯全部在内。

这个方向的代价小得多：量表被当成数值题，只是**信息变少**，均值仍然是合法指标，
不会产生错误叙述。**两个方向的代价不对称，这决定了修复策略（见 §4）。**

---

## 3. 为什么不能靠调阈值解决

语料 21 列（10 量表、10 计数、3 歧义），每列 300 行，确定性生成。

| 状态 | 量表召回率 | 计数变量误判率 |
| --- | ---: | ---: |
| **S0 现状** | 6/10（60%） | 2/10（20%） |
| **S1 只放宽下界** `1<=` → `0<=` | 8/10（80%） | 7/10（**70%**） |
| **S2 S1 + unique 上限 `>10` → `>11`** | 10/10（**100%**） | 10/10（**100%**） |
| **S3 S2 + 列名关键词** | 10/10（100%） | 3/10（30%） |
| **S4 S3 + 「数」后缀规则** | 11/11（100%） | 0/10（0%） |

三条结论：

1. **S1 是半修复。** 0-4 与 0-6 恢复了，**0-10 仍然失效**（11 个取值撞上 unique 上限），
   而误判率已经从 20% 涨到 70%。只改下界的人会以为修好了——在 5 点量表上一切正常。
2. **S2 完全丧失区分力。** 召回 100%，误判也 100%：**每一个计数变量都变成了量表。**
   把 §1 的问题从 20% 放大到 100%。
3. **纯靠阈值不可能两端兼顾。** 必须引入取值之外的信息。

---

## 4. 采取的方案：不放宽判定，只给旁路提示

**决定：`_is_scale_question` 的下界与 unique 上限一概不动，题型词表零改动。**

理由就是 §1 与 §2 的**代价不对称**：现有的保守默认（宁可判成 numeric）是正确方向，
放宽会把代价小的一侧换成代价大的一侧。

改为新增一个**不改变题型**的旁路标记
（`src/question_type_detector.is_scale_candidate`）：

- 条件：整数 + 取值连续 + 范围落在 0-10 内 + 列名无计数关键词 + 尚未被判为量表；
- **题型保持 `numeric question`**；
- `/detect` 每列返回 `scale_candidate`，且仅在 active 类型仍为 numeric 时为真；
- 题型屏在这类列显示「可能是 0-10 量表 · 改为量表题」，点击走**已有的**
  `POST /api/{sid}/types` 覆盖机制。

**信息不足的判断不该假装确定，交给唯一知道答案的人。** 这与 schema 权威链
（`docs/specs/survey-generation-module.md` §11）是同一条原则——不静默采信任何一方，
交人裁决；只是那里的触发条件是"冲突"，这里是"歧义"。

这解决 §2（0 起量表）。**§1 由 §1.2 的降级独立解决**——两者方向相反：
§1 需要收紧（词表降级），§2 需要的是不猜（旁路提示）。

### 4.1 列名启发式（S4）的定位

S4 在语料上拿到 11/11 召回与 0/10 误判。**这个分数本身就是过拟合的读数，
不能作为"问题已解决"的依据**：

1. **语料与启发式同源。** 21 个列名与那套关键词都是我写的；真实平台导出的
   `Q12` / `item_3` / `A1_1` 一个都不在其中。
2. **「排除 `分数/度数`」是给语料打补丁，不是提炼规律。** 每多一个例外，
   就多一分贴着样本走的痕迹。
3. **中文后缀规则不可移植。** `visit_count` 靠关键词命中，`n_kids` 不会。

因此这套词表在实现里的角色是**降低提示噪声的辅助**，而不是判定依据——
它有两处用途，都在安全一侧：抑制 `scale_candidate` 提示噪声（不改变任何东西），
以及 §1.2 的**降级**（只把东西推向保守一侧）。**从不用于把任何列提升为量表。**

## 5. 不可约的歧义（irreducible ambiguity）★

> 这一节是「问卷全流程（survey end-to-end）」定位的核心证据。

```
列名: Q12      取值 0,1,2,3,4      →  5 点量表？还是「孩子数」？
列名: item_3   取值 0,1,...,10     →  NPS？还是「本月购买次数」？
```

**0-10 的 NPS 与 0-10 的购买次数，在取值上完全无法区分。** 取值集合相同、
分布可以相同、缺失模式可以相同。而真实回收数据里，列名常常就是平台生成的
编号，于是 §4.1 的列名信号也一并失效。

**这不是检测器写得不够好，是信息本身不足。** 纯检测（inference from data alone）
在这里没有解——任何阈值、任何词表、任何模型都无法从相同的数字里读出不同的语义。

**只有 schema 能消歧。** 若这份数据来自本工具生成的问卷，schema 里写着
`question_type=scale, points=11, min_value=0`，歧义在生成时就已消除，
回收时只需对齐。

这就是把工具定位为**问卷全流程**而非**通用数据分析**的实质理由：

- **通用数据分析**只拿得到回收数据，注定要在这个歧义上猜；
- **问卷全流程**在生成端就持有语义，回收端只需匹配，**从根上不需要猜**。

fixture 的 `ambiguous` 组（`Q12` / `item_3` / `v7`）把三列固化下来，
测试断言的不是"判对了"，而是**"这三列的判定本质上是掷硬币"**。

## 6. 「识别依据」列：报告依据，不报告概率

题型表原有一列「置信度 / Confidence」，从设计稿以来一直是 `—`。
一个永远为空的列对读者不是中性，是「这里有东西没做完」。

**检测器内部确实有可用信号**：每个判定分支都有阈值，边际总是可算的
（`missing` vs 0.8、`numeric_ratio` vs 0.6、`uniq` ∈ [3,10]、`int_ratio` vs 0.8、
`avg_len` vs 40/25、列名词表命中）。

**但边际不能叫「置信度」。** 实测两行：

```
满意度 (1-5)   uniq=5  int=1.0  range=1-5  in_window=True   → 判 scale
v7    (1-5)   uniq=5  int=1.0  range=1-5  in_window=True   → 判 scale
```

**取值信号完全相同**，唯一差别是列名。纯边际会给 `v7` 打高分——
而 `v7` 正是 §5 记录为掷硬币的列。**给它标「高置信」比留空更糟。**
边际衡量的是「规则触发得多干脆」，不是「答案有多可能对」。

**因此列头定为「识别依据 / Basis」**，回答「我凭什么这么判」：

| 档 | code | 中文 | 何时 |
| --- | --- | --- | --- |
| 高 | `values_and_name` | 取值规律 + 列名一致 | 两个信号互相佐证 |
| 高 | `values_clear` | 取值形态明确 | 文本类，远离判定边界 |
| 高 | `user_override` | 已手动指定 | 用户裁决过——依据就是这个决定 |
| 中 | `values_only` | 仅取值规律，列名无信号 | 取值同时符合量表与计数 |
| 中 | `near_boundary` | 接近判定边界 | 文本类，贴着阈值 |
| 低 | `scale_candidate` | 取值像 0-10 量表，列名无信号 → **改为量表题** | §2 的旁路提示 |
| 低 | `name_demoted` | 列名指向计数，已按此判定 → **改回量表题** | §1.2 的降级 |

**两个「检测器拒绝自行决定」的状态在这一列里有自然归宿**——它们字面上就是判定依据，
不再需要单独的视觉元素。两者都可就地点击，走既有的覆盖机制。

验证：三个已记录为掷硬币的列（`Q12` / `item_3` / `v7`）**全部落在低/中档，
无一被标为高**（已加测试固化）。

## 8. 端到端对照：同一列数据，两条路径 ★

> §5 的不可约歧义是用静态语料论证的。本节是**完整链路跑出来的活演示**：
> 从模板生成一份问卷，导出、合成回收数据、走真实 `/api/upload`，
> 再分别用纯检测和带 schema 两条路径解析同一批数据。
> 对应测试：`tests/test_survey_roundtrip_e2e.py`。

### 8.1 链路

```
build_template("service_satisfaction")     内置模板，零 API key
  → validate_survey()                      0 error
  → export_all()                           5 份产物，含 schema.json
  → generate_responses(n=200)              合成回收数据 + ground truth
  → POST /api/upload                       HTTP 200，真实后端
  → 两条路径分别解析
```

### 8.2 最硬的一条证据：反向计分 ★

问卷里 `srv_wait`（「我要等很久才能收到回复」）是**反向计分题**。

实测（200 行回收数据，**由带潜变量的合成器生成**，见 §9）：

| | 与同构念其他三题均值的相关 |
| --- | ---: |
| 原始值 | **r = −0.506** |
| 按 schema 重编码后 | **r = +0.506** |

两者互为相反数（测试中以 `pytest.approx` 断言）。

> **本表的数字修订过一次，原因值得记下**。初版写的是「原始值 < 0.2、
> 重编码后 > 0.5」，有两处问题：一是数据来自尚未实现潜变量的合成器
> （题项彼此独立，原始相关本就约等于 0，不是"方向相反"）；
> 二是"重编码后"比较的是**构念得分**与其成分题项的均值，
> 存在成分重叠（part-whole overlap），相关高有很大一部分来自
> 构念得分本身就含那三题。现表比较的是**单独一道重编码后的题**，
> 与其余三题，无重叠。

**「哪些题是反向计分」这一信息，在回收的 CSV 里根本不存在。**
它不是编码得不够好、不是列名没起对、也不是检测器不够聪明——
数据里**没有任何一处**记载着「这道题的语义方向与同组相反」。
任何算法、任何模型、任何数量的训练数据都无法从这张表里把它恢复出来。

这是本节最强的论据，因为它**无从辩解**：不像题型可以说「检测器再改改
也许能认出来」，反向计分是**原理上不可恢复**的信息。没有它，
构念得分算出来是错的，而且是**静默错误**——数字照样算得出，只是意义反了。

schema 随行，这条信息就在；不随行，它就永久丢失。

### 8.3 第二条证据：0-10 题型差异

模板里**故意**包含一道标准 0-10 推荐意愿题（`recommend_intent`，
0 = 完全不可能，10 = 极有可能）。

**为什么不回避它**：检测器认不出 0 起量表（§2）。一个务实但错误的做法是
让模板只生成检测器认得出的形态（1 起、3-10 点），这样端到端断言就全绿。
**那是让规则决定什么是好问卷。** 0-10 是推荐意愿、生活满意度阶梯与
WHO 系列的标准形态，模板库里没有它是产品缺陷，不是技术妥协。

这条证据比 §8.2 弱一档，应当如实承认：**它可以被辩解**——
「把检测器的值域放宽不就认出来了？」§3 已经证明放宽的代价是
计数变量误判率升到 100%，但那是一个**工程权衡**，不是原理上的不可能。
所以它是佐证，不是主证。

### 8.4 对照结果（200 行合成数据，13 列）

| 路径 | 反向计分 | `recommend_intent` 判定 | 与 ground truth 不符 | 构念得分 |
| --- | --- | --- | --- | --- |
| **(a) 纯检测**（不给 schema） | **不可恢复** | `numeric question` | {`recommend_intent`} | 算得出但**语义错误** |
| **(b) 带 schema** | 正确重编码 | `scale question` | **∅** | 正确 |

**同一批字节，同一个后端，唯一差别是 schema 是否随行。**

补充：路径 (a) 里那一列的「识别依据」返回 `{level: low, code: scale_candidate}`——
API **明说自己不确定**，而不是猜一个值（§6）。

### 8.5 两条断言都必须绿

测试把最后一步拆成两条独立断言：

- **(a)** 断言检测器的**实际**判定——`recommend_intent` 是 `numeric`。
  这是**已文档化的现状**，不是理想值，**不因此判定测试失败**；
- **(b)** 断言带 schema 时该列解析为量表、反向题正确重编码、构念得分可算。

**要记录的是两条路径的能力差，不是掩盖它。** 若哪天 (a) 突然全绿，
说明检测器行为变了，同样需要 review——断言写的是差异本身。

### 8.6 为什么这比 §5 的静态语料更有说服力

§5 用的是构造语料，说明「原理上不可区分」。本节是**真实链路的产物**：
问卷由模板生成、数据由 schema 合成、上传走真实 HTTP 接口、
解析走真实检测器。**"带 schema 的分析能力严格强于纯检测"不再是设计论断，
而是一条可复现的测试**。

### 8.7 一个过程中的教训（记录以免重犯）

首次实现时，合成器的开放题回答取自 10 条固定短语循环。检测器把该列判成
**多选题**——而且判得有道理：少量小句在多行中反复出现，正是多选题的统计特征。

当时的第一反应是调合成器直到检测器同意，**这是错的**——那等于把测试变成
对合成器的检验而不是对管线的检验。正确做法是让合成数据**真实**
（扩充词表、给每条回答嵌入随机细节使小句唯一），然后**如实断言检测器的输出**。
修正后开放题被正确识别，唯一的检测缺口就是那道 0-10 题。

**准则：调数据去迎合规则，和调规则去迎合数据，是同一种错误的两个方向。**

## 9. 题型检测准确率基准

> 对应测试：`tests/test_detection_accuracy.py`。

### 9.1 数据来源（provenance，务必先读）

**全部数字由带潜变量的合成器生成**（`src/survey_gen/synthetic.py`）：
每位受访者每个构念一个标准化潜分，题项 = 潜分 + 题目噪声。

**修复前的合成器不适合作任何统计量基准。** 那一版的
`_scale_values` 注释声称实现了潜变量，实际每道题独立抽样，
产出的是「披着构念标签的独立列」。用那一版数据算出的 α、
题项-总分相关、构念内相关全部无意义（实测 α = −0.08）。

**因此：不要拿本节数字与 2026-08-01 之前任何合成数据的统计量作比较。**
题型准确率受影响较小（题型判定不依赖题项间相关），但相关性、信度类
指标完全不可比。事故经过见 §10。

### 9.2 语料

3 个内置模板，**合计 37 列**，每档 200 名受访者。

| 模板 | 题数 |
| --- | ---: |
| `service_satisfaction` | 13 |
| `product_usage` | 13 |
| `course_evaluation` | 11 |

**37 列是很小的语料**，这是本基准最大的局限，下节明说。

### 9.3 结果

> **读这张表之前**：下列准确率**不是泛化性能**，不可用于任何"本工具题型识别
> 准确率 97%"式的表述。语料是 **37 列、全部出自我自己写的三个规范模板**，
> 且**合成器与检测器共享同一套"问卷列长什么样"的假设**。
> 这个数字衡量的是**回归**与**各噪声档位之间的相对难度**，不是外部有效性。
> 完整的局限说明见 §9.6。


| 噪声档位 | 准确率 | 说明 |
| --- | ---: | --- |
| `clean` | 36/37（97.3%） | 基线 |
| `missing_15pct` | 36/37（97.3%） | 15% 随机缺失 |
| `scale_as_text` | 36/37（97.3%） | 量表值写成「5分」 |
| `delimiter_mix` | 36/37（97.3%） | 多选混用 `; 、 / ，` |
| `platform_metadata` | 36/37（97.3%） | 额外注入 12 个平台列 |
| `straightliners_20pct` | 36/37（97.3%） | 20% 受访者全选同档 |
| `all_combined` | 36/37（97.3%） | 以上同时开启 |

**七档完全相同，且唯一的错误始终是同一列。** 已验证各档确实改变了数据
（缺失率 0.152、量表值变为「3分」、分隔符由 `;` 变为 `/ ; 、`），
所以这是真实的稳健性，不是噪声没生效。

### 9.4 逐题型指标（clean 档）

| 题型 | P | R | F1 | n |
| --- | ---: | ---: | ---: | ---: |
| multiple-choice | 1.000 | 1.000 | 1.000 | 1 |
| numeric | **0.500** | 1.000 | 0.667 | 1 |
| open-ended text | 1.000 | 1.000 | 1.000 | 3 |
| scale | 1.000 | **0.950** | 0.974 | 20 |
| single-choice | 1.000 | 1.000 | 1.000 | 12 |

### 9.5 混淆矩阵（clean 档，真实 → 预测）

```
scale question           → scale question            19
single-choice question   → single-choice question    12
open-ended text question → open-ended text question   3
numeric question         → numeric question           1
multiple-choice question → multiple-choice question   1
scale question           → numeric question           1   ← 唯一误判
```

**唯一的误判就是那道 0-10 推荐意愿题**（§2、§8.3）。它不是随机误差，
是**每次必现的系统性缺口**，测试对此单列一条断言。

它也解释了 numeric 的 precision 只有 0.500：预测为 numeric 的两列里，
一列是真的数值题，另一列是被漏认的 0-10 量表。

### 9.6 这个基准能说明什么、不能说明什么

**能**：检测回归。任一档位掉到阈值以下即报警，阈值设在实测值之下
（`clean` 0.85 / `all_combined` 0.70），是护栏不是目标——
把阈值卡在实测值上，任何正常波动都会变成失败。

**不能**：

1. **不代表真实准确率。** 合成器与检测器共享我对「问卷列长什么样」的
   同一套假设，97.3% 是这个共享假设的产物，不是外部证据。
2. **语料太小、太同质。** 37 列全部出自我写的三个规范模板，
   没有真实平台导出的脏列名、没有跨语言混排、没有半结构化字段。
3. **七档一致本身也提示语料局限**——一个更大更杂的语料大概率会拉开差距。

**下一步**：接入真实平台导出的列名与列形态是提高本基准可信度的最直接手段，
比继续增加合成噪声档位有价值得多。

## 10. 一段可引用的方法学总结：警惕自己跟自己比 ★

> 本节是下一节（§11）第 4 条的展开，单独成节以便直接引用。

一个数字看起来比它实际更有说服力，最常见的原因不是算错，
而是**它在跟自己比**。这个项目里同一个错误出现过三次，形态各不相同：

**一、成分重叠（part-whole overlap）。** 为证明反向计分题被正确重编码，
我比较了「构念得分」与「该构念中三道正向题的均值」——
而构念得分本身就包含那三道题。相关系数很高，其中很大一部分只是
它跟自己相关。改为比较**单独一道重编码后的题**与其余三题后，
数字才有意义（r 从 −0.506 变为 +0.506，互为相反数）。

**二、语料与规则同源。** 措辞规则的正例、反例语料由我撰写，
而规则也由我撰写。规则在这份语料上表现良好，只能说明
"规则不会在我想到的句子上出错"，不能说明它可泛化。
真正的证据来自一份**从未见过这套规则的人**设计的专业问卷——
在那份问卷上，规则一次触发了 9 条 error，全部是误报。

**三、合成器与检测器共享假设。** 题型识别准确率 97.3% 是在
我自己写的合成数据上测得的，而合成器对"一列问卷数据长什么样"的假设，
与检测器的判定规则来自同一个人的同一套直觉。这个数字可以用来发现回归，
不能用来声称泛化性能。

三者的共同点是：**评估者与被评估者之间存在未被声明的共享信息。**
识别它的方法不是更仔细地检查计算，而是问一个结构性的问题——
**"这个比较的两端，有没有共同的来源？"** 只要答案是有，
数字就必须降级为内部指标，并在文档中明说。

这也是为什么本项目坚持区分两类证据：**护栏**（自建语料、合成数据、
回归阈值）用于发现变化，**证据**（第三方专业问卷、真实平台导出）
用于支持结论。前者不能替代后者，混用就是第二种错误的换皮版本。

## 11. 绿色的测试能掩盖什么 ★

> 这一节不是一个 bug 的记录，是一类失败模式的记录。

### 11.1 事故

`synthetic.py` 的 `_scale_values` 曾带着这样一段注释：

> 「给每个受访者一个潜在倾向，使同构念的题项相关——这正是让信度有意义
> 而不是噪声的东西。」

**代码里没有实现它。** 每道题独立高斯抽样，构念只是一个标签。
注释描述的是意图，代码在做另一件事，而**两者相距很远**。

发现方式：批 3 第一次计算 Cronbach's α，得到 **−0.08**，
全部题项-总分相关约等于 0。

### 11.2 批 2 的 17 个测试为什么全绿

那些测试断言的是**数据的形状**：

- 题型对不对（`scale question`、`single-choice question`…）
- 列数对不对、列名等于 `Question.code`
- 上传返回 200
- 导出产物齐不齐
- 0-10 那列在纯检测下判 numeric、带 schema 判 scale

**没有一条需要题项之间真的相关。** 独立抽样的列，题型一样正确、
列数一样、上传一样成功、导出一样齐全。数据是假的，
但它在每一个被断言的维度上都是真的。

**只有真正计算一个有意义的统计量，才能发现数据是假的。**
α 是第一个需要「同构念题项共享方差」这一性质的量，
于是它一算就露馅。

### 11.3 同一批测试里的第二个问题：成分重叠

批 2 我还报告过一条结论：

> 反向计分题重编码后与同构念其他题的相关性转正（> 0.5），
> 这是反向计分信息不可恢复的证据。

**这条断言当时就是弱的**，与潜变量无关：它比较的是
**构念得分**与其中三道题的均值，而构念得分本身就包含那三题——
存在**成分重叠（part-whole overlap）**，相关高有很大一部分是自己跟自己相关。
**潜变量还没实现、题项彼此独立时，这条断言照样通过。**

修正后的干净检验：单独取**那一道**重编码后的题，与其余三题比较。
原始 r = **−0.506**，重编码后 r = **+0.506**，并断言两者互为相反数。

### 11.4 从中该学到什么

1. **测试断言的维度决定它能发现什么。** 一组只检查形状的测试，
   对内容的真假完全免疫。绿色不等于正确，只等于"被断言的那几件事成立"。
2. **注释不是实现。** 一段描述意图的注释会让读代码的人（包括我自己）
   跳过验证，因为"这里已经写了它做什么"。**注释越自信，越该验证。**
3. **计算一个真实的统计量，是检验数据真假最便宜的手段。**
   它比读代码有效，因为统计量会对数据的性质提要求，而形状断言不会。
4. **警惕自己跟自己比。** 成分重叠、语料与规则同源、
   合成器与检测器共享假设——这三件事在本项目里各出现过一次，
   每次都让一个数字看起来比它实际更有说服力。**展开见 §10。**

现在合成器本身也有测试守着（同构念题项两两相关必须 > 0.15），
潜变量再次退化不会无声通过。
